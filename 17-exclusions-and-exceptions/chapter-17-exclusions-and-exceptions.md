## Overview

As organizations mature, not every alert generated by Cortex requires analyst attention. Some alerts are legitimate false positives; others occur because a security protection conflicts with a business application.

Cortex provides **Exclusions** and **Exceptions** to reduce unnecessary alerts while maintaining operational stability. The two terms sound similar but have very different effects:

- **Exclusions** suppress alerts but keep protection enabled.
- **Exceptions** disable protection itself.

Choosing the wrong one either buries analysts in repeat noise or quietly weakens endpoint security. This is one of the most consequential distinctions a SOC engineer has to get right, precisely because both options *look* like they solve the same problem — a recurring alert that needs to stop.

After investigation: the software is legitimate, the behavior is expected, and the alert appears every day.

## Exclusions vs. Exceptions — The Core Distinction

| Exclusion | Exception |
|---|---|
| Hides alerts | Disables protection |
| Cortex ignores the alert | Agent stops protecting |
| Endpoint still protected | Protection removed |
| Safe for false positives | Used only when necessary |

### Easy Way to Remember

**Exclusion:**
```
Alarm Rings
    │
    ▼
Mute Alarm
    │
    ▼
Security Guard Still Working
```
Protection remains active. Only the alert disappears.

**Exception:**
```
Alarm Rings
    │
    ▼
Remove Alarm
    │
    ▼
Security Guard Leaves
```
Protection no longer exists. The endpoint becomes more vulnerable.

## Issue Exclusions

Issue Exclusions suppress alerts inside Cortex. The Cortex agent still detects the activity, but Cortex no longer displays those Issues.

```
backup.exe
    │
    ▼
Agent Detects
    │
    ▼
Issue Sent
    │
    ▼
Cortex Exclusion
    │
    ▼
Alert Hidden
```

The protection engine still works.

### Creating an Issue Exclusion

```
Right Click Issue
      │
      ▼
 Manage Issue
      │
      ▼
Exclude Issue
```

This excludes only that individual Issue — it is not a reusable rule.

### Exclusion Rules

Instead of hiding one Issue, you can create an Exclusion Rule:

```
   Process
       │
       ▼
   backup.exe
       │
       ▼
Always Exclude
```

Now every matching Issue is automatically hidden.

| Exclude Issue | Exclusion Rule |
|---|---|
| One Issue | Many matching Issues |
| Right-click | Created in Settings |
| Not reusable | Reusable |
| Hidden from table | Visible in Issue Exclusions |

### Case Behavior

Suppose a Case contains Issue A, Issue B, and Issue C. You exclude all three:

```
100%
  │
  ▼
Case Auto-Resolved
```

If another matching Issue appears within 6 hours:

```
New Issue
    │
    ▼
Case Reopens
```

### Best Practices for Exclusions

- Review exclusions regularly.
- Avoid overly broad rules.
- Consolidate duplicate exclusions.
- Audit exclusions periodically.
- Use exclusions only for verified false positives.

## Exceptions

Exceptions are much more serious — they disable the protection that generated the alert.

```
Child Process Protection
        │
        ▼
     Disabled
        │
        ▼
 Application Runs
```

No protection. No alert.

### Why Use Exceptions?

Sometimes business software conflicts with Cortex.

```
Accounting Software
        │
        ▼
Launches Child Process
        │
        ▼
      Blocked
        │
        ▼
  Business Stops
```

The administrator creates:

```
Process Exception
        │
        ▼
Disable Child Process Protection
        │
        ▼
   Application Works
```

### Exception Profiles

Instead of disabling protection everywhere, you create an Exception Profile:

```
Windows Servers
      │
      ▼
Exception Profile
      │
      ▼
Disable Module
      │
      ▼
Applied Only To Servers
```

Profiles provide granular control.

### Common Exception Types

| Type | What It Does |
|---|---|
| **Process Exception** | Disables exploit or malware protection for one process (e.g., disable the injection module for `backup.exe`) |
| **Support Exception** | Created by Palo Alto Support, used temporarily, imported as a JSON file |
| **Behavioral Threat Protection (BTP) Exception** | Disables one specific BTP rule — not all BTP |
| **Local Analysis Rule Exception** | Disables the local analysis rule that generated the alert |
| **Advanced Analysis Exception** | Created automatically after cloud memory analysis determines a memory dump is benign |
| **Digital Signer Exception** | Allows software signed by a trusted vendor certificate to execute |

### Issue Exceptions

Issue Exceptions differ from Exclusions in a fundamental way: instead of Cortex hiding an alert, **the agent stops generating it at all.**

```
Exclusion:               Exception:
  Agent                    Agent
    │                        │
    ▼                        ▼
Alert Generated         No Alert Generated
    │
    ▼
Cortex Ignores
```

**Issue Exception Workflow:**
```
Right Click Issue
      │
      ▼
 Manage Issue
      │
      ▼
Create Issue Exception
      │
      ▼
 Agent Updated
      │
      ▼
Protection Modified
```

### Global Exceptions

Sometimes you want every endpoint to receive the same exception, rather than applying profiles individually:

```
Global Exception
       │
       ▼
  All Endpoints
```

Example: `Disable Rule X` → applied organization-wide.

| Exception Profile | Global Exception |
|---|---|
| Specific endpoints | All endpoints |
| Uses policy | Automatic |
| Granular | Organization-wide |

## Production Example 1 — Windows Script Host Detection

Your Sigma rule repeatedly detects `wscript.exe` running a **signed corporate login script**, every morning.

Investigation confirms: legitimate, approved by IT.

**Best solution:**
```
Issue Exclusion Rule
        │
        ▼
   Hide Alert
        │
        ▼
Protection Remains Enabled
```

## Production Example 2 — Ransomware Detection

Your ransomware rule detects `encryptor.exe`. A developer asks: *"Please create an Exception so it stops blocking."*

The SOC analyst investigates. Threat Intelligence confirms: **real malware.**

**Decision:**
```
   NO Exception
        │
        ▼
Keep Protection Enabled
        │
        ▼
 Investigate Incident
```

**Never create an Exception simply because someone wants an alert to disappear.** This is the single most important judgment call in this chapter — an Exception request should always trigger investigation first, not compliance.

## Production Example 3 — Business Application Crash

A legacy payroll application crashes because Cortex blocks a child process. After testing, the application is confirmed safe.

```
Process Exception
        │
        ▼
Disable Child Process Protection
        │
        ▼
   Only for payroll.exe
        │
        ▼
   Application Stable
```

Notice: only the required protection is disabled — not the whole protection module, not the whole endpoint.

## Decision Flow

```
     Alert
       │
       ▼
False Positive?
       │
      YES
       │
       ▼
Protection Still Needed?
       │
  ┌────┴────┐
 YES        NO
  │          │
  ▼          ▼
Exclusion  Exception
```

## Engineering Insight

A mature SOC follows this order:

```
Investigate → Verify → Exclude (if possible) → Exception (only if necessary)
```

Exceptions are the last resort because they reduce security.

## Best Practices

- Use Exclusions for false positives.
- Use Exceptions only for compatibility issues.
- Prefer Exception Profiles over Global Exceptions.
- Review Support Exceptions after upgrades — these are meant to be temporary.
- Audit all Exceptions regularly.
- Document every Exception.

## Common Mistakes

- Using Exceptions instead of Exclusions.
- Creating Global Exceptions unnecessarily.
- Forgetting to remove temporary Support Exceptions.
- Disabling entire protection modules when only one rule needs adjustment.
- Ignoring periodic audits.

## Key Takeaways

- An Exclusion suppresses alerts in the Cortex console while keeping endpoint protection active — the agent still detects and sends the alert, Cortex just hides it.
- An Exception disables the underlying protection module on the endpoint, preventing both the protection *and* the alert.
- Exclusions are safe for verified false positives. Exceptions are a last resort, used only after testing, business approval, and documentation.
- Global Exceptions apply organization-wide and automatically; Exception Profiles apply to a defined, narrower scope — prefer the latter.
- Experienced SOC analysts treat Exceptions as **security debt** — every Exception creates a blind spot because it disables a protection module. Exclusions simply reduce analyst noise while preserving security.
