## Overview

A **Case** is the primary investigation container in Cortex. While an Issue represents a single security event or alert, a Case groups multiple related Issues into one investigation, providing analysts with a complete view of an attack.

Instead of investigating isolated alerts independently, Cortex correlates related Issues — based on shared hosts, users, processes, timelines, or attack patterns — into a Case. This enables analysts to understand the entire attack lifecycle rather than focusing on disconnected events.

Cases also serve as the central workspace where analysts collaborate, execute Work Plans (Chapter 2), review evidence, perform response actions, and document the investigation until resolution.

## Why Cases Exist

Imagine a ransomware attack generates these detections:

```
PowerShell Execution
        │
        ▼
Credential Dumping
        │
        ▼
Shadow Copy Deletion
        │
        ▼
Mass File Encryption
        │
        ▼
Network Beaconing
        │
        ▼
  DNS Requests
```

**Without Cases:**
```
6 Separate Issues → 6 Separate Investigations
```

**With Cases:**
```
6 Issues → 1 Correlated Case → 1 Investigation
```

This dramatically reduces analyst workload.

## Issue vs. Case

## Case Views

Cortex provides two primary ways to view Cases.

### Table View

Displays Cases in a tabular format. Useful for sorting, bulk operations, filtering, and large environments.

### Split-Pane View

Most analysts prefer this view.

```
   Cases
     │
     ├── List Pane
     └── Details Pane
```

The left pane shows Cases. The right pane shows the selected investigation.

### List Pane

Provides a high-level overview of every Case: Case ID, Case Score, Severity, Status, Assigned Analyst, Starred, Number of Issues.

This allows analysts to prioritize investigations quickly (see Chapter 11 for how starring/severity feed this).

### Details Pane

Contains the complete investigation. Analysts can rename Cases, change severity, assign investigators, update status, execute actions, review evidence, and launch response actions.

Think of it as the command center for the investigation.

## Overview Tab

The Overview tab summarizes the attack: MITRE ATT&CK techniques, attack statistics, severity breakdown, users involved, hosts involved, resource types.

Instead of reading every alert individually, analysts immediately understand the overall attack.

## Key Assets & Artifacts

This tab separates:

**Assets** — entities affected by the attack (hosts, users).

**Artifacts** — evidence collected during the investigation (IP addresses, domains, hashes, filenames, registry keys). Artifacts can also display WildFire verdicts and allow additional investigation.

## Issues & Insights

This tab contains all related Issues.

| Issues | Insights |
|---|---|
| High & Medium severity | Low & Informational severity |

Both contribute context to the investigation. Analysts can also unlink Issues if they do not belong in the Case.

## Timeline

The Timeline displays the attack chronologically.

```
09:01   PowerShell
          │
09:03   Network Connection
          │
09:04   Credential Dumping
          │
09:06   Shadow Copy Deleted
          │
09:08   Encryption Started
          │

```

This helps analysts reconstruct exactly what happened.

## Executions

The Executions tab visualizes process relationships and causality chains (extending the Causality View from Chapter 10 to the full Case).

```
explorer.exe
     │
     ▼

     │
     ▼
powershell.exe
     │
     ▼
```

It allows analysts to identify the root process, follow attack progression, zoom into execution chains, and review process metadata.

## Case Actions

Analysts can perform actions directly from the Case: Assign Case, Change Severity, Change Status, Merge Cases, Create Exclusion, Manage Score, Launch Response Actions. These actions affect the investigation as a whole, not just one Issue within it.

## Case Scoring

Every Case receives a numeric score representing its urgency. Higher scores indicate higher investigation priority. Case scores appear throughout Cortex to help analysts prioritize work.

### Three Scoring Methods

**1. Manual Score** — assigned directly by an analyst. Highest priority.

**2. Rule-Based Score** — calculated using predefined Case Scoring Rules.
```
Malware + Critical Asset → Score 80
```

**3. SmartScore** — AI-powered scoring. SmartScore evaluates:
- Context
- Behavioral patterns
- Statistical prevalence
- Environmental factors
- Historical observations

Unlike static rules, SmartScore continuously adapts as the environment changes.

### Scoring Hierarchy

```
Manual Score
     │
     ▼
Rule-Based Score
     │
     ▼
SmartScore
```

Manual assignments always override automatic calculations.

## Engineering Insight

Cases answer a fundamentally different question than Issues.

**Issues ask:** *"What happened?"*
**Cases ask:** *"What attack is unfolding?"*

The analyst's goal is not to investigate alerts — it is to investigate attacks.

## Best Practices

- Investigate Cases rather than isolated Issues.
- Review the Timeline before taking action.
- Validate the process chain in Executions.
- Use SmartScore to prioritize investigations.
- Assign ownership early.
- Keep Case notes updated.

## Common Mistakes

- Investigating Issues independently.
- Ignoring low-severity Insights.
- Responding before reviewing the Timeline.
- Forgetting to assign Cases.
- Relying only on severity instead of Case Score.

## Key Takeaways

- A Case is the primary investigation container in Cortex.
- Multiple Issues are correlated into a single Case.
- Cases provide a unified workspace for investigation and response — evidence, automation, analyst decisions, and remediation all live in one place.
- The Details Pane contains all investigation information.
- Timeline and Executions help reconstruct the attack.
- SmartScore and Case Scoring help prioritize investigations; manual scores always override automatic ones.
- Mature SOC analysts investigate attacks through Cases, not isolated alerts.
