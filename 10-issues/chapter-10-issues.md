## Overview

An **Issue** is the fundamental investigation object in Cortex. It represents a single security event, suspicious activity, or detection generated by Cortex XDR, third-party integrations, SIEM rules, cloud platforms, or other security products.

Issues serve as the starting point of every investigation. They contain the evidence required to determine whether malicious activity has occurred and whether additional investigation or response is necessary.

As Issues are analyzed, Cortex enriches them with additional telemetry, correlates related events, and may group multiple Issues into a single Case for broader investigation. Understanding Issues is essential because every Case begins with one or more Issues.

## Stitched Issues

One of Cortex's strongest capabilities. A **Stitched Issue** is an Issue that Cortex automatically enriches by correlating endpoint telemetry and related events. Instead of seeing one isolated alert, the analyst receives a complete attack story.

### Stitched Issue Example

Your Windows Script Host with Network Connection Sigma detection fires.

**Initial alert:**
```
wscript.exe
     │
     ▼
External Connection
```

**Cortex stitches additional evidence:**
```
Parent Process
      │
      ▼
  explorer.exe
      │
      ▼
 Child Process
      │
      ▼
  wscript.exe
      │
      ▼
Network Connection
      │
      ▼
 185.100.87.14
      │
      ▼
Downloaded File
      │
      ▼
  invoice.dll
      │
      ▼
Persistence Created
```

Instead of one alert, you now understand the entire attack chain.

## Causality Group Owner (CGO)

CGO is the root process that initiated the attack. Think of it as: **who started everything?**

```
explorer.exe
     │
     ▼
wscript.exe
     │
     ▼
powershell.exe
     │
     ▼
ransomware.exe
```

The CGO identifies where the attack began. Finding the CGO allows analysts to trace malicious behavior back to its origin — this is what a Chapter 17 remote script like `check_file_signature` or a process-tree review ultimately supports: confirming what's actually at the root of the chain.

## Causality View

The Causality View visualizes the attack as a process tree. Instead of reading logs one by one, analysts can see relationships between processes, files, registry changes, and network connections.

```
explorer.exe
   │
   ├── wscript.exe
   │        │
   │        ├── powershell.exe
   │        │         │
   │        │         └── ransomware.exe
   │        │
   │        └── Network Connection
   │
   └── Browser
```

This makes root cause analysis significantly faster than manually correlating separate log entries.

## Key Issue Attributes

Every Issue contains metadata used throughout the investigation:

- Issue Name
- Severity
- Status
- Category
- Source
- Timestamp
- Host
- User
- External ID
- Assigned Analyst

These attributes drive filtering, automation rules, and prioritization (see Chapter 11).

### External ID

Every Issue has an External ID generated by the originating product. For Cortex XDR detections, this often corresponds to the Prevention ID generated by the endpoint agent. The External ID enables analysts to correlate an Issue back to its original source — useful when cross-referencing with a third-party ticketing system or the endpoint vendor's own console.

## Issue Actions

Analysts can perform many actions directly from an Issue:

- Investigate Causality Chain
- Open Timeline
- Create Exclusion Rule
- Retrieve Issue Data
- Retrieve Related Files
- Open Host Risk View
- Exclude Issue
- Change Severity
- Change Status
- Run Automation

These actions allow analysts to investigate without leaving the Issue.

## Working with the Issues Table

The Issues table is where analysts spend much of their investigation time. It allows analysts to:

- Filter Issues
- Sort by severity
- Open summaries
- Launch investigations
- Execute Quick Actions (Chapter 9)
- Change status
- Assign Issues
- Launch playbooks

Think of it as the analyst's operational dashboard for individual detections.

## Engineering Insight

An Issue is not the investigation. It is the starting point.

Good analysts avoid making decisions based on a single alert. Instead they follow:

```
   Issue
     │
     ▼
Stitched Evidence
     │
     ▼
  Context
     │
     ▼
Threat Intelligence
     │
     ▼
Business Context
     │
     ▼
 Decision
```

This reduces false positives and improves response quality — it's the same Context-accumulation discipline from Chapter 4, just applied at the Issue level before automation even starts.

## Best Practices

- Always investigate the full stitched evidence.
- Identify the CGO before containment.
- Review parent and child processes.
- Validate external connections.
- Check the affected user and host.
- Use Causality View whenever available.

## Common Mistakes

- Treating every Issue as an isolated event.
- Ignoring the process tree.
- Skipping threat intelligence enrichment.
- Responding before identifying the CGO.
- Failing to review related telemetry.

## Key Takeaways

- An Issue is the fundamental investigation object in Cortex — every investigation begins with one or more Issues.
- An Issue represents a single security event or detection; a Case is a container that groups multiple related Issues into a single investigation. Cortex automatically correlates related Issues into Cases for a broader view of an attack.
- Stitched Issues provide correlated evidence and attack context, turning one isolated alert into a complete attack story.
- The Causality Group Owner identifies the root process that initiated the attack; Causality View visualizes the complete attack chain as a process tree.
- Analysts should investigate enriched Issues rather than isolated alerts.
- Mature SOC teams use Issues as the starting point for evidence-driven investigations before deciding on containment or remediation.
